# Сбои и деградация — сценарии (20.09.2026, вернуться позже)

Контекст (вопрос 13). Принцип: **падение нашего сервиса не должно увеличивать потери салона от пропущенных звонков** — в любой деградации клиент должен дозваниваться хотя бы до живого человека/автоответчика. Файл — заготовка: реализацию и пороги обсуждаем позже (перед фазой 3).

| # | Сценарий | Что видит клиент | Автоответ системы | Действия человека | Превентивная мера |
|---|---|---|---|---|---|
| 1 | Полное падение call-service / VM | Гудки → переадресация на живого админа/мобильный владельца (настраивается на стороне АТС, не нашего софта) | — | Алерт основателю (24/7), восстановление | Правило «no-answer/failure → на живого админа» обязательно настраивается при подключении каждого салона; healthcheck-мониторинг |
| 2 | SpeechKit (STT/TTS) недоступен или деградация | Бот молчит/отвечает медленно → «секунду, соединяю с администратором» + переадресация | Fallback-провайдер STT/TTS (Whisper API / Silero) через абстракцию | Алерт, переключение конфига | Провайдер за интерфейсом; e2e-таймер латентности с алертом |
| 3 | LLM-ядро недоступно (OpenAI/YandexGPT) | Голос: автоответчик «оставьте сообщение, перезвоним» + запись аудио. Текст: FAQ-режим без LLM + «заявка сохранена» | Fallback-модель в конфиге | Алерт, проверка лимитов/счёта API | Второй LLM-провайдер; тест fallback раз в неделю |
| 4 | CRM (YCLIENTS/Altegio) недоступна/таймаут | Диалог продолжается; бот подтверждает слот голосом | Запись кладётся в очередь (outbox) и создаётся при восстановлении; идемпотентность create_booking | Алерт, контроль очереди | Ретраи; подтверждение слота до create (уже в плане) |
| 5 | Телефонный провайдер упал | Клиент не дозванивается вообще | — | Алерт основателю, тикет провайдеру, SLA-претензия | SLA в договоре с провайдером; для критичных салонов позже — второй номер |
| 6 | «Зависший» звонок (тишина, шум, цикл) | Бот вежливо завершает: «перезвоним вам» | Таймауты: макс. длина звонка, N сек тишины, M неудачных реплик подряд; задача на перезвон | Разбор лога | Тест-чеклист звонков (уже в фазе 3) |
| 7 | Двойная бронь / не та услуга | Клиент получает подтверждение с финальным проговариванием деталей | Подтверждение слота до create_booking; лог + откат; журнал аудита | Разбор инцидента (LIABILITY_OPTIONS.md) | Блокировка create без финального подтверждения |
| 8 | Домен/TLS/вебхуки | Текстовые каналы молчат | Мониторинг сертификатов | Продление/перевыпуск | Алерт за 14 дней до истечения TLS |
| 9 | БД (сбой, потеря данных) | Возможна деградация ответов | Managed PG: автоматические бэкапы + PITR | Restore по runbook | RTO ≤ 2 ч; регламент восстановления |
| 10 | Каскадный сбой YC-региона | Широкая деградация | — | Мониторинг статуса YC, коммуникация салонам | На MVP принимаем риск; позже — multi-AZ/K8s |

## Что решаем позже (вернуться перед фазой 3)

1. Пороговые значения таймаутов и порядок эскалации по каждому сценарию.
2. Фактический выбор fallback-провайдеров STT/TTS и LLM (закупка/доступы).
3. Формат ночного алерта основателю (канал, пороги, дедупликация).
4. Регламент «что говорим салону при сбое» (шаблон сообщения).
