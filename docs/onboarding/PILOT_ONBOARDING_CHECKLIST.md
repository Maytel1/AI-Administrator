## B. Салон клиента в БД

- [ ] **B1. Создать салон** — веб-формы нет, только SQL:

  ```sql
  INSERT INTO salons (name, phone, timezone, plan)
  VALUES ('<Имя салона>', '+7XXXXXXXXXX', 'Asia/Yekaterinburg', 'trial')
  RETURNING id;
  ```

- [ ] **B2. Сохранить `salon_id`** — все шагы ниже выполняются по нему.

## D. Юридическая карточка и биллинг

- [ ] **D1. Карточка плательщика** `/billing` → `legal_save`:
      ИНН — 10 или 12 цифр **с проходящей контрольной суммой**, ОГРНИП/адрес
      обязательны. При ошибке ничего не сохраняется, а в редиректе приходит
      `err=1` с **полным списком ошибок** — прочитать их, исправить и после
      сохранения перезагрузить страницу, убедившись, что данные видны
      (смоук видит только 302 и успех от отказа не отличает).
- [ ] **D2. График автосчёта**: `invoice_due_day` + `auto_invoice` в той же карточке.
      Автосчёт (`auto_invoice_tick`) срабатывает в день `invoice_due_day`,
      **только для plan ≠ trial**.
- [ ] **D3. Смена тарифа с триала**: веб-формы смены `plan` нет → SQL:

  ```sql
  UPDATE salons SET plan = 'start' WHERE id = '<salon_id>';
  ```

  Прайс (`billing.TARIFFS`): trial 0 / start 5 000 / standard 12 000 / pro 15 000 ₽.
- [ ] **D4. Выставить счёт вручную**: `/billing` → `invoice_issue`
      → строка в `payments` со статусом `issued` → отправить текст счёта клиенту.
      ⚠️ Действие доступно **только роли «наша команда»** (право `billing`):
      из-под owner панель ответит «Роли не хватает прав». Владельцу достаточно
      D2 (автосчёт) и D5 (отметить оплату командой).
- [ ] **D5. После оплаты**: `payment_mark_paid` → `paid_until` продлевается,
      `/billing` показывает «оплачен до …». Без этого шага панель вечно
      «Тариф не оплачен».

## Известные подводные камни (по состоянию на 14.10.2026)

1. `legal_save` при невалидных данных **ничего не сохраняет**, но и не «молчит»:
   в редиректе приходит `err=1` с полным списком ошибок (D1). Смоук показывает
   только 302 и текст не проверяет — после сохранения перезагружать карточку.
2. Смены пароля раньше не было — **исправлено 13.10.2026**: `password_change`
   (свой пароль: логин из сессии, старый пароль обязателен) и `password_reset`
   (владелец/team → сотрудник: новый пароль показывается один раз).
3. Задача бэкапа была сломана (>> в аргументах Task Scheduler не редиректит;
   пустой рабочий каталог) — починена 13.10.2026. Если `LastTaskResult ≠ 0`,
   смотреть `backups/backup.log`.
4. Упавший `pg_dump` оставлял **0-байтный** `.dump` — **исправлено 13.10.2026**:
   `backup_db.ps1` удаляет недокачанный/пустой/нечитаемый дамп во всех путях
   ошибки, чтобы битый файл не выглядел как рабочая копия.
5. ~140 тестовых салонов засоряли базу и список выбора точки —
   **устранено 14.10.2026**: разовой чисткой удалено 147 салонов, а источники
   утечки (4 теста: `Chuzhoy salon`, `other-x`, `Tretiy salon`,
   «Другой салон») закрыты очисткой в `finally` — копии больше не копятся.
   `seed_demo` удаляет только пустые салоны с именем из `TEST_NAME_PATTERNS`
   **и без учёток панели**. После прогона `pytest` держать привычку:
   `SELECT count(*) FROM salons` = число живых точек.
6. Последнего активного владельца точки нельзя отключить (`last_owner`) —
   это защита, не баг: перед отключением создать второго owner.
7. `invoice_issue` **не пишет** в `payments` под ролью owner: право `billing`
   есть только у роли «наша команда», HTTP-слой отклоняет действие ещё до
   бизнес-логики. Сверять со снимком `payments` нужно только после прогона
   смоука **под team**.
8. Полный прогон `pytest` раньше **стирал все учётки, платежи, легалки и
   историю входов** живой базы: `test_rollback_keeps_baseline_intact`
   откатывал миграции 005–010 (`DROP TABLE panel_users`, `payments`,
   `client_legal`, `login_log`, колонки `salons.paid_until`) на рабочей БД
   и коммитил результат. **Исправлено 14.10.2026**: откат и повторный накат
   идут в одной некоммиченной транзакции с финальным `ROLLBACK`, а из
   `005_panel_users.sql` убраны собственные `BEGIN/COMMIT` (они рвали внешнюю
   транзакцию). Из-за этого бага исчезали в т.ч. `smoke-owner@test.ru` и
   `demo-owner@test.ru` — после прогона тестов учётки на месте (проверено).
